# prisma-nextjs-blog

Vercel's [Fullstack Blog with Next.js + Prisma](https://vercel.com/templates/next.js/fullstack-prisma-nextjs-blog)
template ([prisma/fullstack-prisma-nextjs-blog](https://github.com/prisma/fullstack-prisma-nextjs-blog))
— a public feed of published posts, drafts, a post page in Markdown, and
GitHub sign-in through next-auth with its Prisma adapter, all read and
written with Prisma — running on **Cloudflare Workers + Static Assets**
through [`@opennextjs/cloudflare`](https://opennext.js.org/cloudflare), with
the database a **Supabase Postgres** project reached through **Cloudflare
Hyperdrive**, both provisioned by Terraform through
[Orun](https://github.com/sourceplane/orun) and the schema applied by Orun's
`db-migrate`, deployed by
[Orun](https://github.com/sourceplane/orun) to stage and prod on every merge.
Packaging it as an Orun baseline is the next milestone (PR2).

The template's code is the code. What the port changes is what the Workers
runtime and a fresh, unattended deployment force:

- The Prisma client is generated for the Workers runtime and built per
  request over the Hyperdrive binding (`lib/prisma.ts`).
- The schema is a migration applied before the app serves, where upstream
  ran `prisma migrate deploy` against `DATABASE_URL`.
- The secret next-auth signs its cookies with is generated by the database
  itself.
- GitHub sign-in is connected by the owner after the build; the blog serves
  its feed signed-out until then.
- The pages read per request instead of at build time; server code reads
  the session with `getServerSession`.
- Publish and delete check that the post is the visitor's own, where
  upstream let any signed-in visitor publish or delete any post.

Next.js moves from 13.5 to 16.3.8, and react-markdown from 8 to 10, for
React 19. Every table in `public` has row-level security, so Supabase's Data
API serves none of it — not a post, not a session token, not an OAuth
token.
See [`specs/epics/prisma-nextjs-blog`](specs/epics/prisma-nextjs-blog/README.md)
for the design, the milestones and the as-built status, including every
departure.

## Getting started

```bash
pnpm install
pnpm run wire:fixture   # re-render apps/web/wrangler.jsonc from its template (committed; this changes nothing)
pnpm typecheck
pnpm lint
pnpm test
pnpm build              # prisma generate + next build + opennextjs-cloudflare build → apps/web/.open-next
```

The build needs no database. Running it locally — a Postgres on
`localhost:54322` (`supabase start`), `pnpm --filter @app/web db:migrate`,
then `next dev` or `wrangler dev` — is in the product's README
(`.baseline/product/README.md`), which is what a product built from here
carries.

## How it maps to Vercel

| Vercel | Here |
|---|---|
| Next.js 13.5 hosting (Pages Router) | One Cloudflare Worker (`.open-next/worker.js`) + Static Assets, on Next.js 16.3.8, still the Pages Router; built with webpack |
| Prisma Postgres or any Postgres (`DATABASE_URL`), one client per process | The Supabase project's Postgres through Hyperdrive: `getPrisma()` builds a `PrismaClient` per request over `@prisma/adapter-pg` from `env.HYPERDRIVE.connectionString`; `DATABASE_URL` is for local work and the Prisma CLI |
| The Prisma client generated for Node.js | `runtime = "workerd"`: the query compiler is a compiled WebAssembly module, left by webpack for wrangler to bundle |
| `prisma migrate deploy` against the production database | `infra/db-migrate` applies `packages/db/src/migrations` per environment — upstream's schema, row-level security, the cookie secret — after the project and the Hyperdrive config exist, before the Worker deploys |
| `SECRET`, set by the owner | Generated once per database into `app_private.secrets`; a `SECRET` Orun secret, pushed as a Worker secret, overrides it |
| `GITHUB_ID`, `GITHUB_SECRET` | Optional Orun secrets per environment, pushed to the Worker as Worker secrets at deploy; unset, no sign-in and a "Log in" page that says how to connect GitHub |
| `NEXTAUTH_URL` | `AUTH_TRUST_HOST`: next-auth reads the origin from each request, so OAuth calls back to the host the visitor is on |
| `getStaticProps` with `revalidate: 10` | `getServerSideProps`: every page reads the database per request, and hands the session to the page |
| A database created in Prisma's or Vercel's dashboard | `infra/terraform/supabase` (one project per environment) + `infra/terraform/cloudflare-hyperdrive` (one config per environment), ids and credentials as orun secrets |
| "Deploy with Vercel" (clone the template) | `orun new --blueprint repo-blueprint.yaml` — a new repository, branded, provisioned, migrated, deployed |

## CI

| Workflow | What it runs | Ships to a product |
|---|---|---|
| `ci.yml` | the Orun pipeline, and the only workflow a product carries: `orun plan --changed`, then one job per lane. A pull request runs the verify lanes (the app built and dry-deployed per environment, both Terraform roots checked and planned, the migrations planned), except the bootstrap's own landings (`orun/BASE-*`), where `plan` alone runs and nothing waits for it — the landing was checked in the build box; a merge applies, migrates and deploys stage → prod. The lanes do not typecheck, lint or run the tests: `baseline.yml`'s e2e tier does, on the landing, before each tag. It plans nothing while `intent.yaml` names the placeholder workspace `ws_CHANGE_ME`, as this repository does. A manual run (Orunbase's Deploy button, or Run workflow on `main`) plans the environment and components it names under the push-to-main trigger, so they deploy as a merge deploys them | yes |
